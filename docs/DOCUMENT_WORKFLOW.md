# Документы v2 в портале

## С чего начать

1. Войти как Owner и открыть **Provider settings** (`/owner/settings/provider`). Заполнить настоящее имя, адрес, контактный email и подтверждённые банковские инструкции. Ikira остаётся брендом, а не отдельной стороной договора. Подтверждения в форме означают проверку введённых данных владельцем, а не юридическую сертификацию.
2. Создать клиента и проект. В карточке клиента указать юридическое имя, платёжный адрес и email; в проекте - описание, стоимость и сроки. Пакет v2 предназначен для USD.
3. Открыть **Documents → New document (v2)**. Выбрать тип и клиента, нажать **Load client & template**, затем выбрать проект и подписанный родительский договор и нажать **Load project & agreement**. Загрузка выбора заменяет несохранённые поля формы.
4. Заполнить поля обычным текстом, сохранить черновик и проверить предварительный просмотр и PDF. Номера документов назначаются автоматически. Имя исполнителя, клиент, проект, связанные номера, цена и заданный срок подставляются из выбранных данных. Остальные условия, даты вступления в силу и предметные критерии нужно проверить и заполнить вручную. `None` / `N/A` допустимы только там, где действительно применимы.
5. Нажать **Send to client** только после проверки. Неполный профиль, пустые поля или неподписанный обязательный родитель блокируют отправку. Сохранение черновика ничего не отправляет.

Перед первой реальной сделкой выполнить проверки из [внутренней памятки](client-documents-v2/INTERNAL_README_RU.md). Генератор не определяет полномочия подписанта, налоговый статус, допустимость банковского счёта или применимость договорных условий.

## Последовательность

| Документ / действие | Как используется |
| --- | --- |
| Proposal | Клиент выбирает переход к MSA / SOW; это не подпись договора и не разрешение начать работу |
| MSA | Выдать PDF, получить необходимые подписи, загрузить подписанный PDF |
| SOW | Привязать подписанную версию MSA; согласовать объём, критерии, цену и сроки; отдельно подписать |
| Advance invoice | В Billing выбрать Advance и подписанный SOW, загрузить предложенную сумму, проверить и выдать счёт |
| Change Order | Привязать SOW и подписать изменение; поле цены означает новую полную стоимость проекта, а не только доплату |
| Delivery & Acceptance | Привязать SOW, указать доставленную версию и доказательства; получить явную приёмку или замечания |
| Final invoice | Выбрать подписанный SOW и принятую версию приёмки; выставить только ещё не начисленную часть |
| Final Handover | Зафиксировать фактическую передачу; подтверждение получения не подменяет выполнение платёжных / правовых условий |
| Care & Support | Отдельно согласовать и подписать обслуживание, привязанное к MSA |

Клиентская загрузка подписанного файла получает статус **Signature received**. Сотрудник с правом управления документами должен открыть файл и подтвердить наличие всех необходимых подписей и согласий. Только после этого версия отмечается подписанной. Владелец также может загрузить уже проверенный подписанный PDF. Это хранение и проверка файла, а не встроенный сервис квалифицированной электронной подписи.

Для приёмки с мелкими доработками заполнить отдельное поле обязательств исполнителя с точными сроками. Список включается в PDF этой версии и в запись решения клиента. Без него такая кнопка недоступна. Не допускать противоречий между этим списком и таблицей замечаний документа. Оплата и молчание не создают запись приёмки.

## Версии и файлы

- **Edit details / create new version** создаёт новый черновик. Старые выданные версии, решения и подписанные файлы остаются в истории.
- Клиент видит только выданные версии своей компании. Новый черновик и его заголовок клиенту не показываются.
- При выдаче новые PDF сохраняются в закрытом хранилище с SHA-256. Изменение имени клиента, банковских реквизитов, шаблона или поступление оплаты не переписывает выданный PDF.
- После изменения профиля создать новую версию ещё не выданного документа. Для черновика счёта доступна **Refresh draft provider details**; выданные счета не обновляются этой кнопкой.
- Если архив отсутствует или повреждён, скачивание выдаёт ошибку. Нужно восстановить оригинальный файл из резервной копии; автоматической замены новым PDF нет.
- Старые документы не переименовываются массово, старые счета без snapshot используют прежнее представление. Если PDF старой записи никогда не сохранялся, восстановить его прежние байты невозможно; первая архивная генерация не является доказательством исторически отправленного файла.
- Клиентские уведомления содержат ссылку на защищённую страницу. PDF не прикладывается автоматически. Для внешних email нужны рабочие SMTP, очередь и доступный клиенту HTTPS `APP_URL`.

## Счета и расчёты

SOW по умолчанию содержит 50% / 50%; автоматические предложения сумм нужно сверять с подписанными условиями. Последний подписанный Change Order меняет общую стоимость. Его новый неподписанный черновик не заменяет предыдущее подписанное изменение.

Пример: согласовано USD 1,000, ранее выдан авансовый счёт 500. Финальный счёт - 500, даже если аванс ещё не оплачен. Портал проверяет общую начисленную сумму и явную приёмку, а не вычитает только полученные деньги. Черновики учитываются в подсказке остатка, чтобы не предложить второй одинаковый черновик; при выдаче проверяются реально выданные счета.

Налоги указываются явно в счёте и должны согласовываться с общей ценой SOW. Налоговый режим не вычисляется автоматически. Отдельный учёт credit notes, зачётов комиссий и налоговых удержаний пока не автоматизирован: использовать проверенные корректирующие документы и внутренний журнал, не записывать такие суммы как фактически поступившие деньги. Обычный счёт без привязки к SOW не получает проверок этапов Advance / Final.

## Обновление и резервные копии

При установке обновления на другом окружении:

```bash
docker compose exec app php artisan migrate
docker compose exec app npm run build
docker compose restart queue scheduler
```

Не использовать `migrate:fresh` на рабочей базе. Английские исходники в `docs/client-documents-v2` должны входить в образ приложения. Изменение Markdown меняет источник будущих документов, но не старые snapshots. Если структура источника поменялась, редактор блокирует повторное использование прежних полей: создать новый документ и проверить его.

Резервировать **базу и закрытые файлы вместе**: `storage/app/private/documents`, `storage/app/private/invoices` и остальные пользовательские вложения. Имеющийся `docker/backup.ps1` делает только SQL-дамп, не полный файловый backup. Доступ к резервным копиям ограничить; проверять восстановление. Не включать реквизиты, документы клиентов, `.env` и токены в Git или публичный каталог.

## Проверки разработчика

```bash
docker compose exec app php artisan test
docker compose exec app ./vendor/bin/pint --test
docker compose exec app npm run build
```

Для локальной визуальной проверки всех семи документов и двух видов счетов:

```bash
docker compose exec -e EXPORT_DOCUMENT_PDF_QA=1 app php artisan test --filter=test_all_pack_pdfs_render
```

Тесты используют SQLite в памяти, поддельное хранилище и отключённые внешние уведомления. Экспорт создаёт только демонстрационные черновики в игнорируемом `tmp/pdfs/portal-qa`; эти файлы не отправлять клиентам. После изменения вёрстки повторно проверить все страницы PDF, особенно длинные поля таблиц.
